# How accurate is Amber's GPU model?

Amber predicts how long a self-hosted LLM takes to answer: time to the first token (TTFT) and to the
last (end to end, E2E). This page checks those predictions against a real GPU server and publishes the
error, including the rows where Amber is badly off.

## What was measured

`calibration/llamacpp_bench.py` ran llama.cpp's `llama-server` (8 parallel slots, continuous batching)
on one machine and timed every request from the moment it was sent:

- **base**: 1, 2, 4 or 8 requests at once × prompts of 128, 512 or 2,048 tokens, 128 output tokens
  each, 3 rounds per cell. A round sends all its requests together and waits for every one.
- **speculative**: one request at a time, with a 1B draft model proposing 2, 4 or 8 tokens per step.

`calibration/fit.py` turned those timings into the profile Amber uses: a prefill cost per prompt token,
a decode cost per step and sequence, and a speculative verification cost.

## How it was checked

`calibration/validate.py` rebuilds each benchmark cell in Amber (one LLM call per request into a
self-hosted LLM set up like the server: 8 slots, a 2,048-token prefill budget) and compares it with the
real run twice.

- **Left-out fitting.** Each cell runs on a profile fitted to every *other* cell's rows, so no cell is
  graded by numbers that already saw its answers.
- **Same traffic as the benchmark.** Amber's GPU scheduler gets the benchmark's own rounds: `c` calls
  at the same instant, the next round when all of them return, 200 rounds. This grades the GPU model
  itself: prefill, decode, batching and speculative decoding.
- **Amber's usual traffic.** A users node sends random arrivals (open loop) at the throughput the
  benchmark sustained in that cell (Req/s). This is how people use Amber, and it is not how the
  benchmark ran: the benchmark is closed loop, so a new round only starts when the last one ends and
  the server never has a line. Pooled over 20 runs of 600 s each. Nothing was tuned to close the gap.

## Real vs Amber

Latencies in ms; error is (Amber − real) / real, so **+** means Amber is slower than reality. "Real n"
is how many real requests the cell has: with 3 to 24 samples, a real p99 is close to the slowest one
seen, so p99 errors are rougher than p50 errors.

## What the numbers say

- **The GPU model holds on this machine.** With the benchmark's own traffic, Amber's median error is
  4–6% on every metric, and 10 of the 12 base cells are within 10% end to end.
- **Long prompts arrive late in reality.** With 4 or 8 prompts of 2,048 tokens at once, Amber's median
  TTFT is 24–33% too fast. Amber prefills one such prompt per step and then moves on; the real server
  gets to the later prompts more slowly.
- **Two at once is cheaper than Amber thinks.** The fitted decode step is `23.4 ms × batch` with no
  fixed part, but a real batch of 2 costs about 39 ms a step, not 47. The c = 2 cells with short
  prompts run 13–18% slow.
- **Speculative decoding is the weak part.** Acceptance was 15% on random-word prompts, and the
  verification cost fits poorly (R² 0.56). Left-out fitting makes that visible: k = 2 and 4 come out
  about 30% fast, and k = 8, predicted from a line fitted to k = 2 and 4 only, is 3× too slow.
- **Open-loop traffic at a full server's pace queues without limit.** On this machine a decode step
  costs the same per sequence at any batch size, so batching adds no throughput: the benchmark's rate
  *is* the server's full capacity. Random arrivals at 100% of capacity form a line that keeps growing,
  which is why most of the second table is off by hundreds or thousands of percent (only the c = 8
  cells, where the batch is full either way, come close). It shows how much Amber's numbers depend on
  how far below capacity a design runs, not that the GPU model is wrong.

## Reproduce

```bash
brew install llama.cpp
python3 calibration/llamacpp_bench.py --model calibration/models/<model>.gguf --draft calibration/models/<draft>.gguf
python3 calibration/fit.py calibration/data/<run> --id <profile id> --gpu-preset <gpu id> --model-preset <model id>
cd backend && uv run python ../calibration/validate.py ../calibration/data/<run> --profile <profile id>
```
